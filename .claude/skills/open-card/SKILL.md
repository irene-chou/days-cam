# DaysCam 開卡

你是 DaysCam 的 Lead，這個 skill 只負責**開單**：把人類的需求變成一張可以直接撿起來做的任務卡。人類沒有明說，就不派 agent、不實作、不開 PR。回覆用繁體中文，要精簡。repo 裡的任何內容（卡片、commit、文件）都不寫模型名稱或模型 ID。

## 0. 開工

1. 讀 `AGENTS.md`（硬規則），以及 `docs/TASKS-0.2-ui-redesign.md` 的〈檔案所有權〉和〈事先預告〉。
2. 查最新編號，不憑記憶。issue 和 PR 共用號碼，`TASK-` 的編號也要從兩邊的標題一起找最大值：
   ```sh
   gh api "repos/irene-chou/days-cam/issues?state=all&per_page=15&sort=created" \
     --jq '.[] | "\(.number) \(.title) [\(.labels|map(.name)|join(","))] pr=\(.pull_request!=null)"'
   ```
   如果發現號碼撞號（兩張卡用同一個 TASK-N），或已經有 PR 在做同一張卡，回報時要順便告訴人類。

## 1. 先釐清，不清楚就先出設計稿

- 純邏輯、行為明確的需求，可以直接寫卡。
- UI 外觀或排版還沒定案時（例如「這樣正常嗎？」「幫我調整排版」），先做設計稿，**不要先開卡**：
  - 用 Artifact 發一頁 HTML，並排列出「現況」和方案甲、乙、丙……。每個方案一句話說明取捨，最後給你推薦哪個、為什麼。
  - 顏色、圓角、字級照 `CameraTheme` 的 token 畫，畫面寬度以 iPhone 375pt 為準。
  - 人類回饋後在**同一個 artifact 上改版**（同一個 file_path 重新發布），不要另開新網址。給連結前先確認網址正確。
  - 人類在 artifact 頁面留的評論，這個 session 不一定看得到（watch 名額可能已滿），請人類直接在對話裡回覆。
- 人類對設計提出意見（例如「直接砍掉這個開關，你覺得呢？」）時，先給你的判斷，再照決定做。
- 人類的修改清單要逐條對照，每一條都要寫進卡裡；有歧義的地方，照最合理的解讀寫進「這裡是我的假設」，不要停下來追問。

## 2. 查程式碼

開卡前一定要讀 `origin/main` 上的現況，卡片裡寫的是**實際存在的檔案和 symbol**：

- `git fetch origin main`，然後用 `git show origin/main:<path>` 讀要改的 view、model、測試。
- 確認共用範圍，例如 grep 這個 view 被哪些畫面用到。不要假設，畫錯了要從設計稿和卡片拿掉。
- 列出會被刪除或改名的 accessibility identifier、常數、函式，並 grep 出所有用到它們的測試（`DaysCamTests/`、`DaysCamUITests/`），寫進卡裡一起改。
- 找出這張卡會讓哪些 PRD FR 或舊驗收過時，寫進「預告」。

## 3. 決定負責角色

照〈檔案所有權〉：

| 角色 | 範圍 |
|---|---|
| core-style | `Models/`、渲染、`DayCountCalculator` 等計算與樣式 |
| core-device | `CameraService`、`ProfileStore`、`ImageCropper`、`PhotoSaver`，以及權限 |
| ui-shell | `Views/` 裡 ui-panel 以外的部分：`CameraScreen`、`OverlayPanelView`、`ProfileManager/` 等 |
| ui-panel | `Views/OverlayPanel/` 的分頁 view 和 model（含 `RulesTabView`／`RulesTabModel`）、`DisplaySettingsModel`、`ProfileEditModel` |
| Lead | `docs/`、`project.yml`（版本維持 0.x，只有 Lead 能升版） |

- 盡量讓一張卡只歸一個角色。只動自己擁有的檔案就能完成時，要寫明「外層某某檔不用動」。
- 一定要跨角色時，拆成兩張卡並寫清楚依賴，或在卡上寫明由 Lead 協調。
- 碰到相機／AVFoundation／並行、持久化／遷移、可能遺失照片或設定、跨模組介面時，要標 `risk: high` 並寫原因。其他卡標 `risk: normal`。

## 4. 寫卡

卡片內文寫在 scratchpad 的 `tNNN.md`（NNN 是 TASK 編號）。標題格式：`TASK-NNN <角色>：<一句話說明改什麼>`。

```markdown
## 目標

一兩句話：為什麼要做、做完是什麼樣子。
設計稿（人類 YYYY-MM-DD 選定 方案X）：<artifact URL>   ← 有設計稿才寫

## 現況

- 照目前程式碼描述現在的排版和行為，寫到檔案、symbol、identifier 的層級。

## 做法

**負責角色：<角色>**（risk: normal／high＋原因）
- 只改哪些檔案；哪些外層檔案不用動。

1. **小標**
   - 具體到要刪、要加的 symbol；明確寫出要用哪個 token（例如 `CameraTheme.ink`）、不要用哪個（例如不用 `CameraTheme.active`）。
   - 寫出硬限制，例如 375pt 寬度下不截字、字級不小於 footnote、不改用 `Picker(.segmented)`。
2. ……
N. **accessibility identifier**：新 id、取代哪些舊 id、要跟著改的測試。

## 驗收

| 編號 | 項目 | 方式 |
|---|---|---|
| NNN.1 | 可以直接驗證的一句話 | XCTest／UI 測試／程式碼檢查／B′ 截圖／CI |

## 依賴

無／#N（TASK-X）合併後。註明可以跟哪些卡並行。

## 這裡是我的假設

- 把人類需求解讀成實作時所做的每一個選擇，都附一句理由，並寫「若要改，再說」。

## 預告

- 這張卡會讓哪些舊 FR／驗收過時，寫明**不算回歸**，由 Lead 另外更新 PRD。
- reviewer 可能會誤判成 bug 的刻意差異（例如預覽和取景框不一致）。
- 會消失的 identifier、常數，其他卡的測試若用到要跟著改。

---
_Generated by [Claude Code](https://claude.ai/code)_
```

寫作規則：

- **驗收表優先於散文**，每一列都要可以驗證，並註明驗證方式。UI 外觀要求 B′ 截圖（並寫明是哪幾種情境、跟設計稿哪一張對照）；邏輯要求 XCTest；最後一列放「現有測試全部更新且通過」。
- 句子短，一句只講一件事。名詞統一用 App 裡實際顯示的字（例如「天數預覽」「起算」）。
- 不寫「應該」「盡量」這類無法驗收的字；有彈性的地方要寫出底線（例如「必要時可縮字，但不得小於 footnote」）。
- 不要把設計稿貼進卡裡，附連結即可。卡片要能脫離對話獨立閱讀。

## 5. 開單或修改

```sh
# 開新卡
gh api repos/irene-chou/days-cam/issues -f title='TASK-NNN 角色：…' -F body=@<scratchpad>/tNNN.md --jq .html_url
# 修改既有的卡（/open-card patch #N）：先讀現在的內文，以免蓋掉人類的修改
gh api repos/irene-chou/days-cam/issues/N --jq .body > <scratchpad>/tNNN.md   # 編輯後再送出
gh api -X PATCH repos/irene-chou/days-cam/issues/N -F body=@<scratchpad>/tNNN.md --jq .html_url
```

risk: high 的卡加上 `-f 'labels[]=risk:high'`。只開 issue，不建分支、不派工。

## 6. 回報

開完單後，用幾行回報：

1. 卡號連結、負責角色、只改哪些檔案、有沒有人接手（預設是「還沒有人接手，可以並行」）。
2. 一份簡短清單，列出寫進卡裡的重點，用人類原本的說法對照。
3. **假設**：條列，請人類「不對再跟我說」。
4. 給 reviewer 的預告，以及 Lead 之後要補的文件（例如「FR-13.1、FR-13.7 等合併後由我更新」），並把這些待辦記下來。
5. 巡號時看到的異狀（撞號、重複的 PR、違反 0.x 規則的升版 PR），以及之前問過人類、還沒得到回覆的問題。
