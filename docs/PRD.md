## 1. 產品目標與非目標

### 1.1 產品目標

DaysCam 是一款 iOS 相機 App，拍照時把日期或天數**即時疊在觀景窗與拍出的照片上**，並將疊字**烘焙進圖片像素**後存入相簿，重現傳統沖印相機「日期印在照片上」的效果。

App 有兩種使用模式：

- **日期模式（預設）**：不需要任何設定，開 App 就能拍，照片上印的是**拍照當下的日期**。這是傳統沖印相機日期戳的原型情境，也服務「我就只想要日期戳、不想管天數」的使用者。詳見 §3.8。
- **計時器模式**：使用者建立一個「計時器」（小孩生日、紀念日、自訂起始日），照片上印的是從起始日算起的天數（或日期＋天數等 6 種模板之一）。

MVP 的成功定義（可驗證）：

| 編號 | 目標 | 驗證方式 |
|---|---|---|
| G-1 | 全新安裝後，使用者**不需任何設定**就能拍出一張印有當天日期的照片 | 刪除 App 重裝 → 開啟 → 按快門，全程不填任何表單 |
| G-2 | 天數計算在所有邊界條件下正確 | `DayCountCalculator` 的 XCTest 全數通過（見 TASK-02） |
| G-3 | 存入相簿的照片，疊字是像素的一部分，任何外部 App 都無法移除 | 用「檔案 App／其他看圖 App」開啟照片，疊字仍在 |
| G-4 | 天數不受照片傳輸影響 | AirDrop 照片到另一台裝置，照片上的天數文字不變 |
| G-5 | 使用者可在 90 秒內完成「首次啟動 → 建立計時器 → 拍出一張帶天數的照片」 | 手動走一次流程並計時 |

## 2. 使用者流程

### 2.1 主流程（Happy Path）

```
啟動 App
  │
  ├─ 首次啟動（尚無任何計時器）──────► 相機畫面【日期模式】
  │                                     疊字＝拍照當下日期（dateOnly）
  │                                             │
  └─ 非首次啟動 ───────────────────────────────┤
     依 lastUsedTimerID 還原上次狀態：           │
       nil    → 日期模式                        │
       有 id  → 該計時器                        │
                                                ▼
                          ┌──────────────────┬──────────────────┐
                          ▼                  ▼                  ▼
                   切換模式／計時器      調整顯示設定          按下快門
                （日期模式 ⇄ 各計時器） （模板/位置/主題）        │
                          │                  │                  ▼
                          └────────►  觀景窗即時預覽疊字   拍照 → 烘焙疊字 → 存相簿
                                                                 │
                                                                 ▼
                                                      顯示成功提示（縮圖 + Toast）
                                                      回到相機畫面繼續拍

  （使用者想要天數時，才自行去計時器列表建立計時器；建立不是必經步驟）
```

### 2.2 首次啟動流程

1. 使用者第一次開啟 App。
2. App 偵測到「尚無任何計時器」，**直接進入相機畫面並套用日期模式**（不放歡迎頁／教學頁，**不強迫建立計時器**）。
3. 相機畫面首次出現時，才觸發**相機權限請求**（iOS 系統彈窗）。
4. 授權後觀景窗即顯示即時畫面，疊字為**拍照當下的日期**（例如 `2026.01.10`），使用者可**立刻按快門**。
5. 使用者第一次按下快門並選擇儲存時，才觸發**相簿寫入權限請求**。
6. 使用者若想要天數，再自行從相機畫面的模式切換入口進入計時器列表建立計時器（見 §3.8、FR-1.9）。

**設計意圖**：把「能拍到第一張照片」的門檻降到零。建立計時器從**必經步驟**改為**可選的加值步驟**。

> **這裡是我的假設（A-3）**：`PROJECT_PLAN.md` 沒有規定權限請求時機。我判定採用「**延遲請求（just-in-time）**」：進入相機畫面才要相機權限，第一次存檔才要相簿權限，而不是 App 一啟動就連續彈兩個權限框。理由是拒絕率較低，也符合 Apple 的建議。

> **這裡是我的假設（A-4）**：首次啟動不提供「示範計時器／範例資料」，也**不自動建立任何 `DaysTimer`**——日期模式是「未選取任何計時器」的狀態，不是一個隱藏的計時器（見 §3.8 與 A-25）。

### 2.3 分支流程：相機權限被拒

| 狀態 | App 行為 |
|---|---|
| 未決定（`.notDetermined`） | 進入相機畫面時彈出系統權限框 |
| 已授權（`.authorized`） | 正常顯示觀景窗 |
| 被拒絕／受限（`.denied` / `.restricted`） | 觀景窗區域顯示**引導畫面**：標題「需要相機權限」、說明「DaysCam 需要相機權限才能拍照並疊上天數。」、按鈕「前往設定」（開啟 `UIApplication.openSettingsURLString`）。快門鍵 disabled。 |
| 使用者從「設定」回來並授權 | App 回到前景（`willEnterForeground`）時重新檢查權限，自動恢復觀景窗，不需重啟 App |

### 2.4 分支流程：相簿權限被拒

App 只需要「寫入」權限，**不需要讀取**相簿。

| 狀態 | App 行為 |
|---|---|
| 未決定 | 第一次要存檔時彈出系統權限框（請求 `.addOnly` 層級） |
| 已授權（含 `.limited`） | 正常存檔 |
| 被拒絕 | 拍照仍可完成（照片已在記憶體中烘焙完成），但存檔失敗。顯示錯誤提示：「無法存入相簿，請到『設定 → DaysCam → 照片』開啟『加入照片』權限。」附「前往設定」按鈕。**此時該張照片會遺失**，需在提示中明確告知：「這張照片尚未儲存。」 |

> **這裡是我的假設（A-5）**：相簿權限被拒時，MVP **不做**「暫存到 App 沙盒待稍後補存」的機制，直接告知照片未儲存。理由：實作暫存佇列會引入額外的檔案管理與生命週期複雜度，超出 MVP 顆粒度。

> **這裡是我的假設（A-6）**：只請求 `PHAccessLevel.addOnly`（僅加入照片），不請求完整相簿讀寫。這同時符合「MVP 不做匯入舊照片」的範圍界定。

### 2.5 分支流程：其他

| 情境 | App 行為 |
|---|---|
| 相機被其他 App 佔用／被系統中斷（來電） | 顯示「相機暫時無法使用」，中斷結束後自動恢復（監聽 `AVCaptureSessionWasInterrupted` / `InterruptionEnded`） |
| 在模擬器上執行（無實體相機） | 觀景窗顯示純色佔位背景 + 疊字預覽，快門鍵 disabled 並標示「模擬器不支援拍照」。**這是給 Dev/QA 用的 fallback，不是產品功能。** |
| App 在相機畫面停留跨過午夜 | 回到前景或系統日期變更時，疊字天數自動更新（見 §6.4） |

> **這裡是我的假設（A-7）**：模擬器 fallback 屬於開發便利性設計，`PROJECT_PLAN.md` 未提及。若 Lead 認為不需要可移除，但這會讓 QA 無法在模擬器上驗證任何疊字相關項目。

## 3. 功能需求

依 `PROJECT_PLAN.md` 的三軸拆解，MVP **只做「MVP 做」那一欄**。

### 3.1 FR-1：計時器管理

| 編號 | 需求 |
|---|---|
| FR-1.1 | 使用者可建立計時器，欄位：名稱、起始日、天數起算規則 |
| FR-1.2 | 使用者可編輯既有計時器的所有欄位 |
| FR-1.3 | 使用者可刪除計時器（需二次確認） |
| FR-1.4 | 使用者可在相機畫面快速切換目前使用的計時器**或日期模式** |
| FR-1.5 | App 記住「上次使用的模式」（日期模式或某個計時器），下次啟動直接套用 |
| FR-1.6 | 名稱為必填，長度 1–20 字元；超出上限時輸入框擋住，不是存檔時才報錯 |
| FR-1.7 | 計時器數量上限 20 個；達上限時「新增」按鈕 disabled 並顯示說明 |
| FR-1.8 | 刪除最後一個計時器後，App **切回日期模式**並停留在相機畫面（**不是**回到建立計時器頁） |
| FR-1.9 | 計時器**不是必要的**：使用者可以完全不建立任何計時器，一直停留在日期模式使用 App |
| FR-1.10 | 使用者可從計時器列表隨時切回日期模式，即使已有計時器存在（日期模式是永久可選的模式，不是過渡狀態） |

> **這裡是我的假設（A-8）**：名稱長度上限 20 字元、計時器數量上限 20 個，皆為 PM 自訂。理由：名稱會疊印在照片上（模板 T5），過長會破壞版面；20 個計時器足以涵蓋 MVP 使用情境，也避免列表 UI 需要分頁。

### 3.2 FR-2：內容格式（模板）

MVP 提供 **6 種預設模板**，使用者從列表中選一種，套用於目前計時器。

**日期模式下的模板限制（FR-2.7，見 §3.8）**：日期模式沒有起始日，除了 `dateOnly` 以外的 5 種模板都無法計算，因此**日期模式下唯一可用的模板是 `dateOnly`**，且不可更改。設定面板在日期模式下仍顯示模板區塊，但只有 `dateOnly` 可選，其餘 5 種為 disabled 並附說明文字（見 A-28）。

範例情境：計時器名稱「小寶」、起始日 `2025-01-15`、起算規則「當天算第 1 天」、拍照當下 `2026-03-20`。
→ 曆法差為 1 年 2 個月 5 天；相差天數為 429 天；套用「當天算第 1 天」後為 430 天。

| ID | 模板名稱 | 輸出格式 | 上述情境輸出 |
|---|---|---|---|
| `dayCountOnly` | 純天數 | `第 {n} 天` | `第 430 天` |
| `unitConverted` | 天數＋單位轉換 | `{Y} 年 {M} 個月 {D} 天`（值為 0 的單位省略） | `1 年 2 個月 5 天` |
| `dateOnly` | 純日期 | `{yyyy}.{MM}.{dd}` | `2026.03.20` |
| `dateAndDayCount` | 日期＋天數並列 | `{yyyy}.{MM}.{dd}　第 {n} 天` | `2026.03.20　第 430 天` |
| `nameAndDayCount` | 名稱前綴＋天數 | `{name} 第 {n} 天` | `小寶 第 430 天` |
| `weekCount` | 週數 | `第 {w} 週又 {d} 天`（餘數為 0 時省略「又 {d} 天」） | `第 62 週又 3 天` |

**模板細則：**

- FR-2.1：`{n}` 為套用起算規則後的天數（見 §3.5）。
- FR-2.2：`{Y}/{M}/{D}` 為 `Calendar` 曆法差（`dateComponents([.year, .month, .day])`），**不套用起算規則的 +1**。
- FR-2.3：`{yyyy}.{MM}.{dd}` 為**拍照當下的日期**，不是計時器起始日。
- FR-2.4：`{name}` 為計時器名稱。
- FR-2.5：`{w}` = 套用起算規則後的天數 ÷ 7 取商，`{d}` = 餘數。以上述情境為例：430 ÷ 7 = 61 餘 3 → 「第 62 週又 3 天」（週數從第 1 週起算）。
- FR-2.6：數字一律使用半形阿拉伯數字，不做千分位分隔。
- FR-2.7：日期模式下只能使用 `dateOnly`，輸出與計時器模式的 `dateOnly` 完全相同（`{yyyy}.{MM}.{dd}`，取拍照當下日期）。

> **這裡是我的假設（A-9）**：`PROJECT_PLAN.md` 的模板清單第 5 項是「自訂前後綴文字帶入變數」，但這與 Phase 4 的「使用者自訂字串樣板（自由文字框插入變數）」界線模糊。我把它收斂成 **`nameAndDayCount`：固定用計時器名稱當前綴**，不提供自由文字框。理由：一旦給自由文字框就等於做了 Phase 4 的項目。**這是本文件中最需要人類確認的假設。**

> **這裡是我的假設（A-10）**：`PROJECT_PLAN.md` 寫「5~6 種」，我補上第 6 種 `weekCount`（週數），因為新生兒常用「第幾週」。若 Lead 覺得沒必要，可刪掉，不影響其他需求。

> **這裡是我的假設（A-11）**：單位轉換模板 `unitConverted` 使用「年／月／天」而非「歲」，因為計時器不一定是小孩生日（也可能是紀念日）。

> **這裡是我的假設（A-12）**：日期格式固定為 `yyyy.MM.dd`，不提供格式選項。理由：格式選項屬於「內容格式」軸的擴張，且 MVP 不做多語系，不需要處理地區化日期格式。

### 3.3 FR-3：位置（9 宮格定位）

- FR-3.1：提供 9 個定位點：左上／中上／右上、左中／正中／右中、左下／中下／右下。
- FR-3.2：設定面板以 3×3 的九宮格按鈕呈現，點擊即套用，觀景窗即時反映。
- FR-3.3：邊距為照片**短邊的 4%**（例如 3024×4032 的照片，邊距為 121pt）。文字錨點依所在格子對齊（左側格靠左對齊、右側格靠右對齊、中間格置中）。
- FR-3.4：預設位置為**右下**。
- FR-3.5：**不提供**自由拖曳（Phase 4）。

> **這裡是我的假設（A-13）**：邊距 4%、預設右下，皆為 PM 自訂。理由：右下是傳統沖印相機日期戳的慣用位置。

### 3.4 FR-4：字體／顏色主題

MVP 提供 **5 組預設主題**。每組主題是「字體 + 顏色 + 陰影／底框」的固定組合，使用者只能整組切換，不能拆開調整。

| ID | 主題名稱 | 字體 | 文字顏色 | 襯底處理 |
|---|---|---|---|---|
| `classicWhite` | 經典白 | System Rounded, Bold | 純白 `#FFFFFF` | 黑色柔和陰影（offset 0,2；blur 4；opacity 0.6） |
| `retroOrange` | 復古橘 | System Monospaced, Bold | 橘黃 `#FF9500` | 黑色陰影（offset 0,1；blur 3；opacity 0.8） |
| `filmStrip` | 底片邊條 | System Monospaced, Bold | 純白 `#FFFFFF` | 半透明黑色圓角底框（`#000000` @ 45%，圓角 8，內距 12×6） |
| `minimalDark` | 極簡黑 | System, Semibold | 近黑 `#1C1C1E` | 半透明白色圓角底框（`#FFFFFF` @ 70%，圓角 8，內距 12×6） |
| `softPink` | 柔粉 | System Rounded, Bold | 粉 `#FF6B9D` | 白色描邊（寬度 2）＋ 淡陰影 |

- FR-4.1：每組主題都**必須**包含陰影或底框，確保在純白／純黑照片上都可辨識（對應 `PROJECT_PLAN.md`「陰影/底色框避免淺色照片文字看不清」）。
- FR-4.2：字級為照片**短邊的 5.5%**，隨照片解析度等比縮放，確保觀景窗預覽與成品視覺一致。
- FR-4.3：預設主題為 `classicWhite`。
- FR-4.4：只使用 iOS 系統內建字體（`.systemFont` / `.monospacedSystemFont` / `.rounded` design），**不打包任何自訂字型檔**。
- FR-4.5：**不提供**自由選色、自訂字型、漸層（Phase 4）。

> **這裡是我的假設（A-14）**：上表的 5 組主題名稱、具體色碼、陰影參數、字級 5.5%，全部由 PM 自訂——`PROJECT_PLAN.md` 只說「4~6 組預設主題（字體+顏色+陰影組合）」。這些數值是視覺設計決策，若 Lead 之後 spawn Design teammate，應由該 teammate 覆蓋本表，並回頭更新本 PRD。

### 3.5 FR-5：天數起算規則

- FR-5.1：每個計時器各自有自己的起算規則（不是全域設定）。
- FR-5.2：二選一：
  - **`dayOne`（當天算第 1 天）**：`n = 曆法相差天數 + 1`
  - **`dayZero`（當天算第 0 天）**：`n = 曆法相差天數`
- FR-5.3：「曆法相差天數」定義為：`Calendar.current.dateComponents([.day], from: startOfDay(起始日), to: startOfDay(拍照當下時間)).day`。兩端都先正規化到當地時區的當日零點，避免時分秒造成的誤差。
- FR-5.4：預設為 `dayOne`。
- FR-5.5：起算規則設定放在**計時器編輯頁**（邏輯層），**不要**跟模板／位置／主題（視覺層）混在同一個設定面板裡（對應 `PROJECT_PLAN.md`「邏輯層獨立於視覺格式之外」）。
- FR-5.6：編輯頁需即時顯示「今天會顯示為：第 N 天」的預覽，讓使用者理解兩種規則的差異。
- FR-5.7：**日期模式沒有起算規則**——它不計算天數，只顯示當天日期，因此不需要、也不提供起算規則設定。

> **這裡是我的假設（A-15）**：預設 `dayOne`。理由：華人文化「第一天」通常指當天本身（如「出生第 1 天」）。

### 3.6 FR-6：拍照與儲存

- FR-6.1：按下快門，使用 `AVCapturePhotoOutput` 擷取照片。
- FR-6.2：在記憶體中把疊字**繪製進圖片像素**（見 §6.2）。
- FR-6.3：以 `PHPhotoLibrary` 將烘焙後的圖片存入系統相簿。
- FR-6.4：存檔成功後顯示 Toast「已儲存」＋左下角縮圖，1.5 秒後淡出，**不跳轉到預覽頁**（維持連續拍攝節奏）。
- FR-6.5：存檔期間快門鍵短暫 disabled，避免重複觸發。
- FR-6.6：**不建立自訂相簿**，直接存進「最近項目」。

> **這裡是我的假設（A-16）**：不建立名為「DaysCam」的自訂相簿。理由：建立自訂相簿需要額外的相簿讀取權限，與 §2.4 的 `addOnly` 最小權限原則衝突。

> **這裡是我的假設（A-17）**：存檔後不跳轉預覽頁、不提供「拍完立即分享」。分享屬於非目標。

### 3.7 FR-7：觀景窗即時預覽

- FR-7.1：觀景窗上疊的文字，其內容、位置、主題必須與最終成品**一致**。
- FR-7.2：預覽的疊字是 SwiftUI 圖層（非烘焙），只有存檔時才烘焙。
- FR-7.3：觀景窗畫面比例與拍攝比例一致（避免「所見非所得」）。

> **這裡是我的假設（A-18）**：拍攝比例固定為 **4:3**（相機感光元件原生比例），不提供 16:9 / 1:1 選項。理由：多比例選項會讓「預覽與成品一致」的驗收複雜度倍增，且比例選項不在三軸分級表內。

### 3.8 FR-8：日期模式

**定義**

日期模式是 App 的**預設狀態**，也是**永久可選的模式**（不是只存在於首次啟動的過渡狀態）。在日期模式下，疊字內容固定為**拍照當下的日期**，格式同 `dateOnly`（`yyyy.MM.dd`）。

| 編號 | 需求 |
|---|---|
| FR-8.1 | 日期模式**不是**一個 `DaysTimer`，而是「**未選取任何計時器**」的狀態 |
| FR-8.2 | **禁止**用「自動建立一個 `startDate` = 今天的計時器」來實作日期模式 |
| FR-8.3 | 日期模式下，疊字文字每次渲染都取**當下日期**，而非任何儲存的日期 |
| FR-8.4 | 日期模式下唯一可用的模板為 `dateOnly`（見 FR-2.7） |
| FR-8.5 | 日期模式下，使用者**仍可自由調整位置（9 宮格）與主題（5 組）**，偏好需持久化（見 §4.2） |
| FR-8.6 | 日期模式下沒有「名稱」與「起算規則」概念，這兩項設定不出現 |
| FR-8.7 | 日期模式在計時器列表中呈現為一個**固定項目**，可被選取，但不可編輯、不可刪除 |
| FR-8.8 | 日期模式與計時器模式在拍照、烘焙、存檔流程上**完全相同**，照片本身無任何差別標記 |

**FR-8.2 的理由**

若用「自動建立 `startDate` = 今天的計時器」來假裝日期模式，使用者**明天**打開 App 會看到「第 2 天」而不是當天日期，完全違背這個變更的目的。日期模式必須是一個沒有起始日、每次都重新取當下日期的狀態。

**與計時器的關係**

| 情境 | 行為 |
|---|---|
| 尚無任何計時器 | 日期模式，列表中只有「日期模式」一個項目 |
| 已有計時器，使用者選了日期模式 | 日期模式；計時器全部保留，不受影響 |
| 在日期模式下建立第一個計時器 | 自動切換到新建立的計時器（見 A-27） |
| 在日期模式下建立第 2 個以後的計時器 | 同上，自動切換到新建立的計時器 |
| 刪除最後一個計時器 | 自動切回日期模式（FR-1.8） |
| 刪除的計時器**不是**目前選取的 | 目前模式不變 |

> **這裡是我的假設（A-25）**：日期模式的**表示方式**為 `lastUsedTimerID == nil`（§4.2）；日期模式自己的位置／主題偏好存在 `UserDefaults` 的兩個獨立鍵（`dateModePosition`、`dateModeTheme`），**與各計時器的偏好互不影響**（在日期模式改成左上，不會動到任何計時器的位置設定，反之亦然）。人類只拍板了「日期模式＝未選取任何計時器」與「位置/主題要有地方存」，具體鍵名與「互不影響」這個語意是我決定的。

> **這裡是我的假設（A-26）**：日期模式在計時器列表中**固定顯示為第一列**，標題為「**日期模式**」、副標為「只印當天日期」，沒有編輯與刪除入口（左滑無刪除動作）。選取時與其他列一樣顯示選取標記。

> **這裡是我的假設（A-27）**：使用者建立新計時器後，App **自動切換到該新計時器**（而非留在原本的模式）。理由：使用者會去建立計時器，通常就是為了立刻使用它。

> **這裡是我的假設（A-28）**：日期模式下的設定面板，模板區塊**仍顯示全部 6 種**，但 `dateOnly` 以外的 5 種為 disabled 且加上說明文字「需要先選擇一個計時器」。另一個選項是「整個模板區塊隱藏」，我選擇顯示但 disabled，理由是讓使用者看得到「建立計時器後可以解鎖什麼」，這也回應了 §9.2 Q-6 的可發現性疑慮。

## 4. 資料模型

### 4.1 `DaysTimer`

| 欄位 | 型別 | 說明 | 約束 |
|---|---|---|---|
| `id` | `UUID` | 唯一識別碼 | 建立時產生，不可變 |
| `name` | `String` | 計時器名稱 | 1–20 字元，必填 |
| `startDate` | `DateComponents`（year/month/day） | 起始日，**只存年月日，不存時分秒** | 見 §4.3 |
| `countingRule` | `CountingRule` | `.dayOne` / `.dayZero` | 預設 `.dayOne` |
| `templateID` | `TemplateID` | 6 種模板之一 | 預設 `.dayCountOnly` |
| `position` | `OverlayPosition` | 9 宮格之一 | 預設 `.bottomTrailing` |
| `themeID` | `ThemeID` | 5 組主題之一 | 預設 `.classicWhite` |
| `createdAt` | `Date` | 建立時間 | 系統填入 |
| `updatedAt` | `Date` | 最後修改時間 | 系統填入 |

### 4.2 App 層級狀態

| 欄位 | 型別 | 儲存位置 | 預設值 | 說明 |
|---|---|---|---|---|
| `lastUsedTimerID` | `UUID?` | `UserDefaults` | `nil` | 下次啟動要套用的模式。**`nil` 代表日期模式**（§3.8 FR-8.1）；有值則代表該計時器 |
| `dateModePosition` | `OverlayPosition` | `UserDefaults` | `.bottomTrailing` | **日期模式專用**的疊字位置偏好（FR-8.5） |
| `dateModeTheme` | `ThemeID` | `UserDefaults` | `.classicWhite` | **日期模式專用**的主題偏好（FR-8.5） |

**語意細則：**

- `lastUsedTimerID` 為 `nil` 是**正常狀態**，不是錯誤，不需要 fallback 到任何計時器。
- `lastUsedTimerID` 指向一個**已不存在**的 id 時（例如資料損毀），視為 `nil` → 進入日期模式，**不要**退回第一筆計時器。
- `dateModePosition` / `dateModeTheme` 與 `DaysTimer.position` / `DaysTimer.themeID` 是**完全獨立**的儲存，互不覆蓋（A-25）。
- 日期模式**沒有**對應的 `templateID` 欄位——它恆為 `dateOnly`，不需要存（FR-8.4）。

### 4.3 儲存方式

- 所有 `DaysTimer` 以 `Codable` 序列化成單一 JSON 檔，存於 `Application Support/DaysCam/timers.json`。
- 寫入採**原子寫入**（先寫暫存檔再 `replaceItem`），避免寫入中途被中斷導致資料損毀。
- `startDate` **不存 `Date`（絕對時間點）**，改存年／月／日三個整數。理由：`Date` 是 UTC 絕對時間點，使用者跨時區移動時，同一個 `Date` 可能被解讀成不同的當地日期，導致天數跳動（見 §6.3）。

> **這裡是我的假設（A-19）**：採用「JSON 檔 + Codable」而非 Core Data / SwiftData。理由：MVP 資料量極小（上限 20 筆），Core Data 的 schema migration 成本不划算，且 `CLAUDE.md` 傾向不引入不必要的複雜度。若 Lead 認為未來要做雲端同步（非目標），再由 Dev teammate 提出改動提案。

> **這裡是我的假設（A-20）**：`startDate` 以年月日整數儲存。這是一個**架構決策**，會影響 TASK-02 / TASK-03 的介面設計，請人類優先確認。

## 6. 技術硬約束

> 以下兩點是**硬約束**，任何 teammate 不得繞過。若實作上發現無法達成，必須回報 Lead，不得自行改變做法。

### 6.1 硬約束 1：天數必須以「按下快門當下的系統時間」計算，禁止依賴 EXIF

**規定：**

1. 天數計算的「現在時間」來源，一律是按下快門當下讀取的 `Date()`（透過可注入的時間來源，方便測試）。
2. **禁止**在專案中出現任何讀取照片 EXIF 時間戳（`kCGImagePropertyExifDateTimeOriginal` 等）作為天數依據的程式碼。
3. **禁止**把「檔案建立時間」當作拍攝時間的備援。
4. MVP 不提供「匯入相簿舊照片並疊字」的功能，架構上根本不接觸 EXIF。

**理由：**

競品 BabyAgeCam 踩過這個坑——若以照片 EXIF 時間戳計算天數，照片透過 AirDrop、社群平台、雲端備份等途徑傳輸後，EXIF 可能被剝除或改寫，導致同一張照片在不同裝置上顯示不同天數。DaysCam 把天數在拍照當下就烘焙進像素，天數成為不可變的事實，徹底避開這個問題。

**未來若要做匯入功能（Phase 4）的原則**（先寫在這裡備查，MVP 不實作）：有 EXIF 就用 EXIF；沒有或數值不合理時，**必須跳出 UI 讓使用者手動輸入拍攝日期**，絕不能默默用檔案建立時間充數。

### 6.2 硬約束 2：疊字必須烘焙進圖片像素

**規定：**

1. 儲存到相簿的圖片，疊字必須是圖片**像素資料的一部分**。
2. **禁止**用「另存疊字圖層 + 另存原圖」「寫入 metadata」「存成可編輯的浮水印物件」等任何事後可移除的做法。
3. 實作方式：以 `UIGraphicsImageRenderer` 在原始尺寸的 context 上先繪製原圖，再繪製疊字，輸出成新的 `UIImage`，最後才交給 `PHPhotoLibrary`。
4. 烘焙時必須正確處理 `UIImage.imageOrientation`，避免文字在直向拍攝時被旋轉 90 度。
5. 烘焙後的圖片不保留「原圖無疊字版本」。

**理由：**

`PROJECT_PLAN.md` 的產品定位是「重現傳統沖印相機把日期印在照片上的效果」。若疊字可被移除，照片離開 App 後就失去了 DaysCam 的核心價值；同時這也是 §6.1 的配套——唯有烘焙進像素，天數才不會隨照片傳輸而跑掉。

### 6.3 衍生約束：時區

- 所有日期比較一律使用 `Calendar.current`（跟隨裝置當前時區與曆法設定）。
- `startDate` 存年月日整數，在計算當下才用 `Calendar.current` 還原成當地零點（見 §4.3）。
- 效果：使用者從台北飛到紐約，「2026-01-01 開始」的計時器在紐約當地的 2026-01-10 仍顯示「第 10 天」，不會因時差變成第 9 或第 11 天。

> **這裡是我的假設（A-21）**：跨時區採「一律用裝置當前時區」而非「鎖定建立時的時區」。理由：使用者的直覺是「今天是幾號」跟著所在地走。`PROJECT_PLAN.md` 把「時區邊界等進階規則」列在 Phase 4，所以 MVP 只需要這個簡單一致的規則，不處理更細緻的情境。

### 6.4 衍生約束：跨午夜更新

- App 需監聽 `NSCalendarDayChangedNotification` 與 `UIApplication.willEnterForegroundNotification`。
- 收到通知時，重新計算並更新觀景窗疊字。
- **烘焙時必須當場重新計算天數**，不得沿用畫面上快取的字串——避免「App 在相機畫面停留跨午夜，畫面沒更新就按快門」導致存下錯誤天數。

## 7. 邊界條件與錯誤處理

### 7.1 天數計算邊界

| 情境 | 規定行為 |
|---|---|
| 拍照日 = 起始日 | `dayOne` → 第 1 天；`dayZero` → 第 0 天 |
| 跨月 | 依實際曆法天數，不是「月數 × 30」 |
| 跨年 | 依實際曆法天數 |
| 閏年（起始日或區間含 2/29） | 2/29 必須被算進去 |
| 起始日為 2/29，當年非閏年 | 見下方 A-22 |
| 起始日在未來 | 見 §7.2 |
| 天數超過 9999 | 正常顯示，不截斷、不縮寫 |
| **日期模式** | 不進行任何天數計算；上述邊界皆不適用。疊字恆為當下日期，**不可能**出現「尚未開始」或負數 |

> **這裡是我的假設（A-22）**：起始日為 2/29 時，`unitConverted` 模板的「年」進位交由 `Calendar` 原生行為決定（Foundation 的 `dateComponents` 會把 2024-02-29 → 2025-02-28 算成 0 年 11 個月 30 天，而非滿 1 年）。MVP **接受系統原生行為**，不特別處理。純天數模板不受影響。此行為需在 TASK-02 的測試中固定下來，避免未來 OS 版本改變時無聲失效。

### 7.2 起始日在未來

- **UI 層**：計時器編輯頁的日期選擇器**上限設為今天**，使用者無法選到未來日期。
- **邏輯層**：`DayCountCalculator` 仍必須對「起始日 > 今天」有定義行為，因為使用者可能手動把系統時間往回調。規定行為：回傳 `n <= 0` 的原始計算值（`dayOne` 規則下，起始日比今天晚 9 天會得到 `-8`），由**顯示層**負責轉成使用者可讀的文字：所有模板一律顯示 `尚未開始`。
- 疊字仍會烘焙「尚未開始」四個字，不阻擋拍照。

> **這裡是我的假設（A-23）**：UI 擋未來日期 + 邏輯層回傳負數 + 顯示層轉成「尚未開始」，這整套處理方式 `PROJECT_PLAN.md` 未提及。另一個合理選項是「顯示倒數 N 天」，但那等於新增一種內容格式，超出 MVP 範圍，故不採用。

### 7.3 錯誤處理

| 錯誤 | 使用者看到 | 技術處理 |
|---|---|---|
| 相機權限被拒 | 權限引導畫面 + 「前往設定」 | 見 §2.3 |
| 相簿權限被拒 | 「無法存入相簿…這張照片尚未儲存。」+「前往設定」 | 見 §2.4 |
| 相機硬體不可用 | 「相機暫時無法使用」 | 見 §2.5 |
| 存檔失敗（磁碟空間不足等） | 「儲存失敗：{系統錯誤描述}。請確認裝置儲存空間後再試一次。」 | 捕捉 `PHPhotoLibrary` 的 error 並顯示 |
| `timers.json` 讀取失敗／格式損毀 | 見下方 A-24。**回復後進入日期模式**，使用者仍可立即拍照 | — |
| `lastUsedTimerID` 指向已不存在的計時器 | 無錯誤提示，靜默進入**日期模式**（§4.2） | 視為 `nil` |
| 烘焙過程失敗（記憶體不足等） | 「照片處理失敗，請再試一次。」 | 不存檔，不顯示成功 Toast |

> **這裡是我的假設（A-24）**：`timers.json` 損毀時的處理方式為：**把損毀檔案改名保留成 `timers.json.corrupt-{timestamp}`，以空清單啟動，並在 App 內顯示一次性提示「計時器資料讀取失敗，已重設。」**。理由：靜默清空會讓使用者無從察覺，直接崩潰又更糟。
