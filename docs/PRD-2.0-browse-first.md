## 0. 這次為什麼改

1.x 的做法是拍照當下把天數烘焙進照片。人類 2026-10-28 的判斷：**使用者會因為字破壞了照片而不想用**；而且天數紀錄是長期、零星的行為，使用者平常用內建相機拍，不會特地開第三方相機。

2.0 的主軸改成：**照片不動、瀏覽時即時標天數、匯出時才烘焙**。DaysCam 從「另一台相機」變成「整理與標記照片的工具」。人類明確的主要情境：**平常內建相機拍、之後再整理**。

體例沿用 0.1／0.2：表格與條列是規範；`> 為什麼…` 的引文是理由。這裡沒寫到的沿用前幾版；被覆蓋的條目列在 §9。

## 2. 範圍

### 2.1 名詞

| 名詞 | 意思 |
|---|---|
| **紀錄** | 2.0 對「設定檔（`CameraProfile`）」的使用者稱呼：一個名稱、一個起始日、一組照片、一組疊字樣式。程式碼型別名稱不改 |
| **相簿** | 「照片」App 的使用者相簿（`PHAssetCollection`，`.album` / `.albumRegular`）。**一個紀錄綁一個相簿**，相簿是紀錄照片的單一事實來源 |
| **即時標記** | 畫面上畫在縮圖或大圖之上的天數文字，不寫進任何檔案 |
| **匯出** | 把疊字烘焙進像素，存成一張**新的**照片到「最近項目」；原圖不動 |

### 2.2 分期

| 期 | 內容 | 本文件 |
|---|---|---|
| **2.0 第一期** | 紀錄列表、紀錄綁相簿、照片牆即時標天數、加入照片（系統選照片器）、大圖、單張匯出（疊字形式，沿用現有樣式面板）、相機縮減成只存乾淨原圖、舊資料遷移 | §3～§8 全部 |
| 第二期 | 拍立得框匯出形式、多選匯出、色調與裁切比例移到匯出頁、對比圖 | 只在 §2.4 保留接縫 |
| 第三期 | 演進影片 | 同上 |

### 2.3 第一期不做

- 拍立得框（第二期，匯出頁先只有「疊字」一種形式，但版面照 D-7 預留切換列的位置）
- 多選、對比圖、影片
- 匯出時的色調與裁切（第一期匯出用原圖尺寸與比例，色調固定 `standard`）
- 按日期區間或 AI 自動歸類照片進紀錄；只認相簿
- 每張照片手動改拍攝日期（在「照片」App 裡改即可，見 §6.1）
- 影片與 Live Photo 的動態部分：相簿裡的影片**不顯示**；Live Photo 只當靜態照片
- 訂閱／IAP／追蹤 SDK、iPad（沿用既有裁定）

### 2.4 給後期留的接縫

- 匯出頁頂端的形式切換列（「疊字」）第一期只有一個選項，可以只顯示不可切換，或整列先不畫，由實作者決定；資料模型保留 `ExportFormat` 列舉（`overlay`、`polaroid`），存在紀錄裡，第一期恆為 `overlay`
- `OverlayRenderer.bake` 維持 6.5.4：「影像 → 烘焙後影像」，不綁來源。拍立得框是在 `bake` 之外先鋪畫布再呼叫 `bake`，第一期不實作
- 照片牆的格線 `cell` 要能進入多選狀態（第二期），第一期不實作但不要把點擊寫死成只能進大圖

### 3.1 畫面清單（取代 0.2 §3.1）

| 畫面 | 說明 | D-7 |
|---|---|---|
| 紀錄列表 | App 首頁。列出所有紀錄；右上 `plus` 新增 | 1 |
| 紀錄編輯 | 名稱、起始日、相簿、天數規則（沿用 0.2 FR-13 的內容，改成獨立頁）。新增與編輯同一頁 | 從 2 的 ⋯ 進入 |

| 照片牆 | 一個紀錄的照片，依月份分段、由舊到新，每格即時標天數 | 2 |
| 大圖 | 單張照片、套紀錄樣式的即時標記、匯出入口 | 3 |
| 匯出 | 預覽＋現有的內容／樣式／位置面板；打勾存新照片 | 4 |
| 相機 | 從照片牆底部進入。拍一張乾淨原圖存進這個紀錄的相簿 | 2 底部 |
| 權限頁 | 相簿權限被拒或受限時的說明與「前往設定」 | — |

0.2 的「相機畫面（首頁）」「頂部設定檔選單」「管理設定檔」「照片瀏覽（D-5）」「圖庫設定」全部被取代（§9）。

### 3.2 主流程

```
啟動
 ├─ 第一次啟動：自動建一個紀錄「我的紀錄」（起始日＝今天，沿用 0.1 預設）→ 紀錄列表
 └─ 既有使用者：遷移（§4.3）→ 紀錄列表
紀錄列表 ─點一列─► 照片牆（第一次進任何紀錄時請求相簿權限 §7）
 ├─ 右上 plus ─► 紀錄編輯（新增）
照片牆
 ├─ 點縮圖 ─► 大圖 ─ 匯出 ─► 匯出頁 ─ 打勾 ─► 存成新照片 → 回大圖，VoiceOver 唸「已匯出」
 ├─ 底部「加入照片」─► 系統選照片器 ─► 選的照片加進相簿 → 牆更新
 ├─ 底部相機 ─► 相機 ─ 快門 ─► 乾淨原圖存進相簿 → 回照片牆或繼續拍
 └─ 右上 ⋯ ─► 編輯紀錄／刪除紀錄／（第二期：選取多張、對比圖、影片，第一期不顯示）
大圖
 └─ 右上 ⋯ ─► 從紀錄移除（＝從相簿移除）／刪除照片（系統確認）
```

## 4. 資料模型

### 4.1 `CameraProfile` 欄位變更（其餘欄位沿用 0.2 §4.1、PRD-0.2 §4.1 的 1.1.0 增補）

| 欄位 | 變更 | 型別 | 說明 |
|---|---|---|---|
| `albumIdentifier` | **新增** | `String?` | 綁定相簿的 `PHAssetCollection.localIdentifier`，可以是 DaysCam 建的，也可以是使用者在紀錄編輯頁挑的**既有**相簿（FR-21.4，人類 2026-10-28 決定支援）。`nil` 表示還沒綁（新紀錄沒挑、或遷移來的舊設定檔）；第一次加入照片、或相機第一次存檔時才建一本同名相簿並寫入 |
| `fallbackAssetIDs` | **新增** | `[String]` | 紀錄自己記的照片 ID。**限制取用**模式下這就是紀錄的全部照片（只顯示其中仍在限制集合內者，§7.3；2026-10-31 人類裁定）；完整權限時照樣可以有值（遷移來的舊照片 §4.3），顯示時與相簿內容**聯集、去重** |
| `exportFormat` | **新增** | `ExportFormat` | `overlay`／`polaroid`，預設 `overlay`，第一期恆為 `overlay`；缺欄位或未知字串退回預設 |
| `position`、`style`、`showDayCount`…等疊字欄位 | 語意改變 | 不變 | 從「拍照時烘焙的樣式」變成「這個紀錄的**匯出樣式**與**即時標記樣式**」。匯出頁改的就是這些欄位，改完即存，下一次匯出沿用 |

DaysCam 自建的相簿名稱＝紀錄名稱；已有同名相簿時**仍另建**（「照片」App 允許重名；想用既有那本的人會在編輯頁挑）。紀錄改名時**不**跟著改相簿名（相簿是使用者的東西，由他自己管）；相簿被使用者刪掉時，`albumIdentifier` 查不到 → 視同 `nil`，下次加照片再建一個，`fallbackAssetIDs` 不受影響。兩個紀錄可以綁同一本相簿（不擋，只在挑選時標示「已被「<紀錄名>」使用」）。

> 為什麼相簿是單一事實來源：人類 2026-10-28 要求「在照片 App 整理」與「在 DaysCam 裡選」兩種都支援。兩邊都寫同一個相簿，就不需要兩種身分的照片，也不會出現「這張是手動加的、那張是相簿來的」的同步問題。

### 4.2 App 層級狀態

- `CapturedPhotoStore`（`photos.json`，0.2 §4.4）在遷移後退役：內容搬進 §4.3 指定的紀錄的 `fallbackAssetIDs`，檔案保留不刪（下一版再清），之後不再寫入
- `AlbumSettingsStore` 的「存到 DaysCam 相簿」開關與 `daysCamAlbumIdentifier` 退役（§9）；「另存無疊字副本」（#610／#611）**整張作廢**，不實作
- `CaptureSettingsStore`（比例、色調、閃光等）：相機只留閃光、前後鏡頭、變焦、計時器；比例與色調的欄位保留在檔案裡不讀，第二期匯出頁再用
- 新增 `selectedProfileID` 的語意：改為「上次打開的紀錄」，只用來決定相機與匯出的預設，不再有「目前設定檔」的 UI 概念

### 4.3 舊檔轉換（1.3.0 → 2.0）

| # | 規則 |
|---|---|
| M-1 | 所有設定檔原樣保留，新增欄位用預設值；遷移不得遺失任何設定檔（沿用硬規則） |
| M-2 | `photos.json` 裡的 ID **原樣、不過濾**全部放進**遷移當下 `selectedProfileID` 指的那個紀錄**的 `fallbackAssetIDs`（這裡是 Lead 的假設：1.x 的照片沒有紀錄歸屬，一位真實使用者，放進最後使用的紀錄最接近他的預期）。遷移時沒有讀取權限（1.x 多數只拿過 `.addOnly`），所以不得在遷移時查相簿過濾；已刪除的照片由 FR-17.2 顯示時過濾 |
| M-3 | 不把舊照片搬進任何相簿、不建相簿、不請求權限；遷移在啟動時純本機完成。1.x 若有 `daysCamAlbumIdentifier`（#281 的「DaysCam」相簿），直接寫進 M-2 同一個紀錄的 `albumIdentifier`，不查證是否存在（存在與否由 §4.1 的「查不到視同 nil」處理） |
| M-4 | 遷移前先備份 `profiles.json` 為 `profiles.v1.json`（一次性），遷移成功才寫新檔；失敗則維持舊檔並以舊版本號重試下次啟動 |
| M-5 | 1.x 烘焙過的照片在 2.0 顯示時會被再疊一次即時標記（字會重複）。接受；這是舊照片，不做特別處理 |

## 6. 天數計算的來源（**修訂 0.1 §6.1，這是硬約束的變更**）

### 6.1 圖庫照片的拍攝時刻＝`PHAsset.creationDate`

| # | 規則 |
|---|---|
| 6.1.1 | 相簿裡每張照片的「拍攝時刻」一律取 `PHAsset.creationDate`，**透過 0.1 §6.5 的顯式參數**（`DayCountCalculator(now:)`、`TemplateRenderer.render(capturedAt:)`）餵進計算與渲染層；各層仍不得自行讀時鐘 |
| 6.1.2 | 日曆日以 `Calendar.autoupdatingCurrent`（現在的時區）從 `creationDate` 換算（沿用 0.1 §6.3）。在別的時區拍的照片可能因此差一天，**接受**，不讀 EXIF 時區、不做進階時區規則 |
| 6.1.3 | `creationDate` 為 `nil` 的照片：牆上標「日期不明」、不算天數、大圖可看、不能匯出 |
| 6.1.4 | **仍然禁止**：讀 EXIF（`CGImageSource`、`kCGImagePropertyExif*`）、讀檔案建立時間、任何自行解析影像 metadata 的程式碼。唯一允許的來源是 `PHAsset.creationDate` |
| 6.1.5 | 使用者覺得日期不對，去「照片」App 用「調整日期與時間」改；DaysCam 透過 FR-17.8 自動跟著更新。這取代 0.1 §6.5「沒有 EXIF 就跳 UI 手動輸入」的 Phase 4 原則 |

> 為什麼：0.1 §6.1 禁 EXIF 的理由是「照片經傳輸後 EXIF 會被剝除，天數跑掉」。2.0 的天數是**瀏覽時即時算**的，照片本來就在使用者自己的圖庫裡，`creationDate` 是「照片」App 自己顯示給使用者看的那個日期，使用者已經把它當事實，而且可以在那裡改。匯出成品一樣把天數烘焙進像素，傳出去之後不變，0.1 的核心保證仍成立。

### 6.2 拍攝時刻早於起始日：「前 N 天」

| # | 規則 |
|---|---|
| 6.3.1 | **照片**（牆、大圖、匯出）的拍攝時刻早於起始日時，文字一律是「前 N 天」（N＝起始日與拍攝日的日曆日差，不受 `countingRule` 影響；前一天＝「前 1 天」）。牆、大圖、匯出三處文字必須相同 |
| 6.3.2 | **「今天」**（紀錄列表的「今天第 N 天」、相機 HUD）在起始日為未來時維持 0.1 §7.2 的「還有 N 天」倒數文字，不變 |
| 6.3.3 | 實作：`TemplateRenderer.render` 的呼叫端分得出「照片」與「今天」兩種情境，由實作者決定是加參數還是分函式；既有倒數測試不得刪，另補「前 N 天」測試。只印日期（`showDayCount` 關）時不受影響 |

> 為什麼：1.x 只有「現在」一種時刻，負值一定是起始日在未來。2.0 的照片有過去的時刻，對一張兩個月前的照片印「還有 60 天」是錯的語意。

### 6.3 烘焙只發生在匯出（**修訂 0.1 §6.2**）

- §6.2 第 1～4 點改為「**匯出的**照片必須烘焙進像素」，匯出走的仍是 `OverlayRenderer.bake`，介面不變（6.5.4）
- §6.2 第 2 點「禁止另存原圖」、第 5 點「不保留無疊字版本」**刪除**：原圖本來就在相簿，匯出是另一張新照片
- 相機存的乾淨原圖不經 `bake`，是刻意的，不是回歸（寫進 CONVENTIONS 易誤判處）

## 7. 權限

| # | 規則 |
|---|---|
| 7.1 | 第一次點進任何紀錄（照片牆）時請求 `.readWrite`。說明文字（`project.yml` 的 `NSPhotoLibraryUsageDescription`）改為「DaysCam 需要讀取相簿來顯示每張照片是第幾天，並把你挑的照片整理進紀錄的相簿。照片本身不會被修改。」 |
| 7.2 | `.authorized`：全部功能 |
| 7.3 | `.limited`（限制取用）：看不到相簿也不能改相簿，而且 `PHPicker` 選出的照片若不在限制集合裡，之後也讀不到（不可依賴 picker）。這時紀錄的照片＝**該紀錄 `fallbackAssetIDs` 中仍在限制集合內的照片**（2026-10-31 人類裁定，#640；原「App 可見的全部照片 ∪ `fallbackAssetIDs`」讓每個紀錄看到同一批照片，實機回報令人疑惑）。App 可見但沒有紀錄記下的照片不出現在任何紀錄；使用者從限制集合取消勾選的照片讀不到、自然不顯示，`fallbackAssetIDs` 不清除。「加入照片」改開 `presentLimitedLibraryPicker(from:completionHandler:)`，把回傳的**新勾選** ID 去重後附加到**當下這個紀錄**的 `fallbackAssetIDs`（系統只回傳這次新勾選的；原本就在限制集合內的照片不會回傳，因此不會被加入，已知限制）；相機存檔走 `.addOnly` 路徑並把 ID 寫進當下紀錄的 `fallbackAssetIDs`（App 自己建的照片在限制取用下可讀，0.2 A-7）。遷移來的舊照片只在 §4.3 指定的紀錄。照片牆頂端常駐一行「限制取用中，不會與「照片」App 的相簿同步」。`albumIdentifier` 不建不用 |

| 7.5 | 匯出存檔不另外請求權限（已有 `.readWrite` 或 `.limited` 都允許新增） |
| 7.6 | 0.2 FR-5.3′「存檔只請求 addOnly」在 2.0 不再適用（因為進紀錄就要讀相簿）；AGENTS.md 的對應 review 規則要同步改 |
